# MUCOCO reproduction: archived failures and a fresh model sample

Author: Ajnas N B. October 1, 2026.

We distinguish three things: our checker bugs, the author's saved consistency
failures, and new behavior from the current Azure model. They must not be counted
as one set of AI-discovered security vulnerabilities.

## Author-result replay — zero Azure calls

The pinned MUCOCO repository links Figshare article `30402541`, version 2,
“MuCoCo: Code Consistency Testing Framework Replication Package.” We obtained its
results archive and replication package, verified their supplied MD5 checksums,
and recorded SHA-256 hashes. The Figshare artifacts declare CC BY 4.0; this does
not establish a blanket redistribution license for every GitHub checkout.

We executed the author's unchanged RQ1 `standardize_two_df` definition and
`DataLogHelper.compare_code_generation_dataframe_results` on the saved
GPT-4o HumanEval few-shot output-prediction original/Boolean-literal CSV pair.
We did not run the entire MongoDB/GPU/notebook environment.

The author comparison returned 14 original-correct/mutant-incorrect rows and
17 rows in the reverse direction, over 220 comparison-eligible rows from
1,111 task IDs. Eight of the 14 forward failures are Markdown/output-format
differences. Six are wrong values. This is one archived slice, not the full
paper's aggregate failure rate.

For a meaningful demonstration, we selected the first wrong-value case per
distinct function in numeric task-ID order and stopped at three. This is
explicitly **known-positive reproduction**, not an unbiased discovery sample.

| Archived case | Correct output from both programs | Saved original model answer | Saved mutant model answer |
|---|---|---|---|
| `HumanEvalTF447`: `is_happy("iopaxioi")` | `False` | `False` | `True` |
| `HumanEvalTF466`: `prime_length("aaaaaaaaaaaaaaa")` | `False` | `False` | `True` |
| `HumanEvalTF547`: `skjkasdkd([8191, 123456, 127, 7])` | `19` | `19` | `26` |

All six original/mutant programs passed their HumanEval author tests and
produced the expected selected-input output in the isolated no-network
worker. All three saved inconsistency classifications were independently
confirmed. The original outputs were replayed, **not regenerated by GPT-4o**.
These are output-prediction consistency failures, not invoice-access leaks.

Exact cases, source excerpts, original/mutant hashes and replay evidence are in
`evidence/mucoco-author-replay-v1` and `mucoco-author-replay-v1.json`.
The upstream license/attribution record is `THIRD_PARTY_LICENSES/mucoco-figshare-attribution.md`.

## Fresh Azure attempt — separate negative result

Before querying the model, we froze HumanEval/0, /1 and /3 with one selected input
each, rename/Boolean-literal operators and unchanged repeats. The actual author
AST transformer and `OutputPrediction.zero_shot_prompt` were loaded unmodified;
unused GPU/database imports were bypassed. Every applicable mutant passed the
author's tests before inference.

There were 11 fresh Azure GPT-6.1 Sol output-prediction queries: originals,
validated mutants and unchanged repeats. HumanEval/1 has no applicable Boolean
literal, so that variant was skipped rather than treated as a successful test.

All 11 answers were correct. Across five applicable original/mutant comparisons,
the original-correct/mutant-incorrect pattern occurred **zero times**, with zero
unknown comparisons. The reference estimate was **$0.009928**.

This small fresh sample did not reproduce an inconsistency on the current model.
The three archived positive cases are not added to its denominator, and we did
not keep replacing examples or paying for retries until an error appeared.
The original-paper failure pattern is demonstrated by the archived replay, not
claimed as a newly observed Sol failure or replication of published accuracy.

Evidence: `protocols/mucoco-prediction-v1.json`, `mucoco-model-v1.json` and
`cost-accounting-v4.json`. The previous canonical-solution mutation smoke remains
historical and is not relabeled as a model-level experiment.
